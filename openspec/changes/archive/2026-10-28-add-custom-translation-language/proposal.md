# 自定义释义语言

## 为什么要做

目前释义语言跟着界面语言走，用户不能单独指定自己看得懂的语言。我们希望用户可以填写“法语”“韩语”“繁体中文”等语言，让词义和语法说明都按这个选择生成，同时继续使用已经配置好的模型和 API Key。

## 会改哪些地方

- 设置页增加“释义语言”输入框：留空表示跟随界面语言，填写后点击“保存”生效；重启后保留选择。
- 按本次确认的方案，统一保留英文提示词，在分析请求中指定回答语言；无需先调用 API 翻译提示词，也无需等待生成模板。
- 词级和短语级的 `meaning`（释义）、`grammar`（语法说明）统一使用目标语言。日语原文、读音、词性标记和结构字段保持原有约定。
- 提示词明确区分“语言名称用什么文字填写”和“最终用什么语言解释”：“法语”“French”“français”都指向法语解释。目标语言规则统一约束全部解释字段，不跟随提示词、界面、原文或示例的语言自行改变。
- 每次开始句段分析时读取当前生效语言，缓存按“句子原文＋语言名称”区分。有效语言变化时清空缓存，后续分析使用新设置；已显示的结果等下一次识别时正常更新，保存设置本身不发起网络请求。
- 界面按钮和提示仍跟随现有中英文界面设置。允许填写任意语言名称，实际生成效果取决于用户选择的模型。
- 首版不提供提示词编辑器、自动翻译整份提示词、语言检测或新的界面语言包。

## 能力范围

### 新增能力

- `custom-translation-language`：填写、校验、保存和恢复释义语言；计算本次分析真正使用的语言；与界面语言分别控制。

### 调整已有能力

- `i18n-llm-prompts`：提示词统一使用英文，回答语言来自本次分析的语言设置，同时覆盖词义和语法说明。
- `llm-protocol-abstraction`：三种现有协议遵守相同的释义语言要求，保留各自的结构化输出方式。
- `llm-word-meanings`：去掉词义和悬停弹窗中固定“中文释义”的限制。
- `llm-phrase-groups`：短语组合的释义和语法说明使用目标语言，缓存查询同时检查语言是否匹配。
- `english-dictionary`：悬停弹窗引用目标语言的模型释义，保留本地词典查词与读音流程。
- `llm-result-cache`：缓存按句子原文和语言名称匹配，语言变化时清空，保留原有容量及淘汰规则。
- `staged-overlay-analysis`：语言设置作用于后续识别；保证下次识别不因原文相同而跳过分析，保留原有覆盖层刷新流程。
- `localization`：界面本地化继续生效，分析提示词不再随界面文化翻译。

## 影响范围

- 核心层：新增简单的释义语言偏好接口；分析请求只携带语言名称字符串，调整缓存匹配及重复文本判断。
- 应用层：调整设置页、设置页视图模型、依赖注入，以及用于界面显示的中英文资源。通过现有 `ISettingsService` 保存偏好，不新建配置文件。
- 平台层：调整 `PhrasePromptBuilder`，将英文分析模板与界面资源分开管理；保留现有模型、认证、协议和结果解析流程。
- 验证范围：设置与持久化、三种协议的请求内容、缓存复用、保存后重新识别的语言变化，以及现有架构检查。
- 开发和验收使用假服务检查请求与行为，不调用用户的真实模型服务。
