# 自定义释义语言：实现设计

## 背景

目前 `LanguageService` 管理中英文界面，`PhrasePromptBuilder` 从界面资源中读取提示词。因此，界面语言和释义语言绑在一起。英文资源的词级指令还残留“生成中文释义”的要求，容易与英文短语释义发生冲突。

另外，`PhraseAnalysisOrchestrator` 的缓存只按句子原文查找。增加语言设置后，缓存需要同时区分语言，避免下一次分析同一句日语时仍然复用另一种语言的释义。

本设计承接[提案](proposal.md)，说明功能边界与实现方式。

## 目标与范围

要实现：用户单独设置释义语言；开始分析时读取当前设置；英文提示词直接指定回答语言；缓存按语言区分。

本次不做：翻译或编辑整份提示词、新增界面语言包、多源语言 OCR、自动判断回答是否真的用了目标语言、额外的语言验证请求。

## 设计决定

### 一、只保存一个可选的语言名称

设置页在现有大模型设置附近增加以下内容，标题和说明继续提供中英文界面资源：

| 界面内容 | 用户看到的含义 |
| --- | --- |
| 释义语言输入框 | 可填“法语”“한국어”“繁体中文”等，也可以留空 |
| 输入框说明 | 留空时跟随界面语言；实际效果取决于所选模型 |
| 保存按钮 | 校验通过后才更新生效设置 |
| 当前生效语言 | 明确显示本次会用哪种语言解释 |

不用额外的模式开关。空值就是“跟随”，非空值就是“自定义”，避免两项设置互相矛盾。

通过 `ISettingsService` 使用新键 `ExplanationLanguage` 保存用户填写的值；空值删除该键。现有 `Language` 键继续只表示界面语言，API 地址、模型、Key 等设置也不改变。

输入先去掉两端空白。去掉后为空视为跟随；非空时限制为 1～80 个字符，拒绝内部换行和控制字符。输入无效时展示界面语言对应的错误，保留原来的生效设置。首版不维护语言白名单，也不把名称自动转换成语言代码，因此“法语”和“French”都能填写，但不合并为同一个缓存身份。

用户不需要知道目标语言自己的拼写。输入框说明应举例说明：“可填写中文名、英文名或该语言自己的名称，例如法语、French、français；请填写明确的语言名称。”这些名称由模型理解；软件仍按原始名称保存和比较，不额外请求模型统一名称。

视图模型保存的是“正在编辑的草稿”；只有点击保存才更新生效偏好。这样输入到一半时不会反复清缓存。保存相同的规范化值不重复清缓存。

### 二、界面语言与有效释义语言分别计算

在 Core 的 `PhraseAnalysis` 切片内定义一个小的释义语言偏好接口，在 App 实现并注册为共享实例。App 负责读取设置、读取界面语言、保存偏好和通知语言变化；Core 只需要取得当前语言名称，不直接读取文件或解析界面资源。沿用现有能力切片及其依赖方向。

“有效语言”指本次真正会要求模型使用的语言：

| 保存的自定义值 | 界面语言 | 有效释义语言 |
| --- | --- | --- |
| 空 | 简体中文 | 简体中文，发给模型时用 `Simplified Chinese` |
| 空 | 英文 | 英文，发给模型时用 `English` |
| 法语 | 简体中文或英文 | 法语，发给模型时保留用户的语言名称 |

用户设置了法语后，再切换界面语言，不改变有效语言，也不清理法语缓存。保存后有效语言值完全相同时，不重复清缓存；除此之外，不猜测不同语言名称是否等价。

### 三、分析时读取当前语言

`PhraseAnalysisOrchestrator` 每次开始句段分析时读取当前生效的语言名称，用于缓存查询和 `PhraseAnalysisRequest`。请求只增加一个语言名称字符串，`PhrasePromptBuilder` 用这个字符串填写英文指令中的目标语言。

同一个请求的提示词与缓存使用同一个语言名称。结果成功后，按该请求实际使用的语言写回缓存，保持匹配关系清楚即可。

首版按“先设置，再使用”的通常流程设计。设置变化作用于之后开始的句段分析，已经开始的请求按原有流程完成，不额外取消或重做，也不要求整批请求锁定同一次设置。

### 四、英文模板与界面翻译分开管理

将现有分析提示词整理为 Platform 层内部的英文模板，继续由 `PhrasePromptBuilder` 选择协议对应的版本。这里只保存模型指令，不新增 Core 或 Platform 的界面本地化资源。

模板明确要求：用请求指定的语言填写 `groups[]` 和 `words[]` 中的 `meaning`、`grammar`；保留 JSON 字段名、标识、日语原文、读音以及现有日语词性标记。词级指令不能再固定要求中文。

#### 输出语言规则必须说清楚

只附上“目标语言：法语”还不足以表达全部要求。三种协议的固定系统指令都要包含以下规则；下面用中文说明，实施时仍写成英文模板：

1. **按名称所指的语言解释。** 用户的语言名称可能用中文、英文或该语言自己的文字填写。例如“法语”“French”“français”均表示用法语生成解释，不表示用填写名称时所用的文字回答，也不是让模型解释“法语”这个词。
2. **以本次目标语言为准。** 英文提示词、中文界面、日语原文以及结构示例的语言，都不能替代目标语言。示例只说明结构，示例值不能照抄进回答。
3. **所有解释字段保持一致。** `groups[]`、`words[]` 的 `meaning` 和 `grammar` 都用目标语言书写，不一部分中文、一部分英文，也不额外附上双语解释。解释中确有需要引用的日语原词和例句可以保留，但说明这些内容的文字仍使用目标语言。
4. **只改变解释文字。** JSON 字段名、词元标识、组标识、日语词头、原文标签、读音及约定的词性标记继续保持原样；语言要求不能破坏结构化输出，不增加语言声明字段或 JSON 之外的说明。
5. **不自行更换语言。** 指令禁止因提示词是英文、名称写成中文或模型不确定，就自行改用英文或中文。目标值只作为语言名称数据，不作为新的操作指令。

例如，用户填写“法语”后，请求表达的完整意思是：“用这个名称所指的法语，解释本次日语句段；所有词义和语法说明都用法语；日语词头与结构字段保留。”用户不需要先把“法语”改写成 `French`。

这些规则明确的是**我们要求模型做什么**，不是程序对实际输出语言的强制校验。当前 JSON 结构约束只能限制字段和类型，不能证明其中的文字属于法语。遇到无法识别的名称或模型不遵守要求时，首版仍可能得到不符合语言要求的内容；现有“不自动检测、不额外重试”的范围保持不变，不能宣传为保证语言正确。

用户填写的语言名称以转义后的独立数据值插入固定指令，不把输入当成任意提示词模板执行。继续遵守现有请求大小限制、结构解析和语义校验。首版不增加语言识别器，也不宣称能阻止模型的一切误解。

三种协议共用目标语言和分析规则，但仍保留各自的输出要求：

| 协议 | 继续使用的输出方式 |
| --- | --- |
| OpenAI Chat Completions | JSON 对象模式及结构示例 |
| Anthropic Messages | 强制调用现有结构化结果工具 |
| OpenAI Responses | 现有严格 JSON 结构声明 |

不改变认证、接口地址回退、模型选择和字段约定。移除不再使用的提示词资源及其引用，保留弹窗标题、“无释义”等界面资源。默认构造分析器时也必须取得真实英文模板，不能再用资源键名充当提示词。

### 五、换语言后清缓存，下次识别使用新设置

缓存匹配条件改为“句子原文＋语言名称”，仍然只缓存成功结果，最多 50 条，满后淘汰最早加入的条目。有效语言变化时调用现有清空缓存的方法，一并清理关联的会话分组标识。

保留现有缓存读写和识别发布流程。尚未完成的请求返回后，按它实际使用的语言正常处理；语言变化本身不增加请求拦截逻辑。

已经显示的释义、短语组和弹窗继续保留，等下一次识别按现有流程更新。目标临时隐藏或恢复、普通增量合并等行为继续沿用原有规则。

这不是一次新的识别：保存设置不运行 OCR，也不调用模型。界面会提示“释义语言已更改，下次识别生效”。下一次手动识别或实际发生的自动识别使用新语言。

还需要清掉 `WordOverlayApplicationService` 中用于跳过重复文本的 `_lastRecognizedText`。否则下一次自动识别即使启动，仍可能因“日语原文没变”而跳过分析。自动识别的画面变化检测继续按原规则运行，保存语言不主动制造识别事件。

普通增量识别继续按现有流程合并和刷新；换语言后的下一次识别会重新分析当前文本，再替换显示内容。

### 六、失败时沿用现有回退

没有配置模型、未启用分析、超时、拒绝或结构错误时，仍使用现有失败处理和本地读音回退。保存语言不需要 API Key，也不探测模型是否支持该语言。

如果模型返回了结构正确但语言不符合要求的内容，首版不自动识别、不静默改成另一语言，也不额外重试。用户可以换一个名称更明确的语言或调整模型。这是模型能力的限制，应在设置说明中讲清楚。

## 风险与取舍

- 不同模型对小语种的能力不同 → 界面说明“允许自定义语言，效果取决于模型”，验收主要检查请求是否正确表达要求，不用单次联网结果证明支持所有语言。
- 在分析过程中修改语言 → 已开始的请求按原流程完成，新设置用于之后开始的分析；按已确认的使用习惯接受这种边界情况，保留上述简单规则。
- 同一语言存在多个写法 → 首版保留用户输入，不增加语言别名库；最坏结果是重新分析一次。
- 英文模板迁移可能遗漏协议差异 → 对三种协议分别检查请求，保留已有结构化输出和结果校验测试。
- 切换后暂时没有新释义 → 明确提示下次识别生效，保留已完成的本地读音信息，不自动增加网络调用。

## 迁移与回退

旧用户没有 `ExplanationLanguage` 键，启动时自然进入“跟随界面语言”，不需要转换旧配置。缺失、类型错误或格式无效的语言值也按跟随处理，不导致启动失败。

部署时只新增这一个偏好键；不迁移界面语言、模型和认证配置。缓存本来只在内存里，升级重启后自然清空。若回退到旧版本，新键由现有设置服务保留，旧版本继续使用原来的界面语言行为。

## 待确认事项

没有阻塞本次实施的产品问题。方案已确认采用“英文提示词＋指定释义语言”。首版按上述空值含义、保存时机和下一次识别生效规则实施；细节验收见各项规格。
